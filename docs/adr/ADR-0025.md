# ADR-0025: Windows のツール所有は mise を唯一の正本とし、実行確認で壊れを検出する

- Status: Accepted
- Date: 2026-11-20
- Extends: ADR-0006, ADR-0021
- Related: Issue #206

## Context

Windows の machine-global ツールは `mise.global.toml` で宣言し、mise が導入する。しかし実機では次の 3 つの問題が同時に存在した。

### 1. Machine PATH が mise shim に勝つ

Windows は Machine PATH を User PATH より先に評価する。mise の shim は User PATH (`%LOCALAPPDATA%\mise\shims`) にあり、`Program Files` 配下の vendor コピーは Machine PATH にある。そのため `node` / `gh` / `nvim` / `rg` は、mise が管理しているにもかかわらず vendor コピーが解決されていた。

`verify.ps1` はこれを FAIL として報告していたが、修正手段が無かった。README の PATH 所有ルールは「同名の重複は自動では削除しない」としており、解消は各 installer のアンインストールに委ねられていた。

### 2. 存在確認では実行時の破損を検出できない

`Get-Command devin` は成功するのに `devin --version` が `the devin-win32-x64 package is not installed` で失敗した。mise の npm backend が作る `node_modules/.mise/<pkg>@<ver>` 配下の内部依存が完全でないと、この形で壊れる。

- devin 固有ではなく、`playwright` の内部依存を削除しても同じ `MODULE_NOT_FOUND` が再現した。
- `mise install <tool>` は "already installed" と判断して修復しない。

`verify.ps1` のツール確認は `Get-Command` による解決だけだったため、この破損を検出できず、壊れた環境を「converged」と報告していた。

### 3. 旧 Rust home が残存

`%USERPROFILE%\.rustup` (1.3 GB) と `%USERPROFILE%\.cargo` (92 MB) が残っていた。ADR-0021 は「参照されないが不可逆なので残す」としていた。

## Decision

### mise を唯一の所有元とする

`mise.global.toml` に宣言されたツールについて、実行時の解決先は mise でなければならない。Machine PATH 上の vendor コピーが干渉する場合、machine はその entry を除去する。

`platforms/windows-11/mise-path-ownership.ps1` がこの操作を行う。

- 判定の正本は `mise which <name>`。ディレクトリ内の各実行ファイルについて、mise が同名の実体を解決できるかを調べる。
- 全件が mise 提供なら除去対象、1 件でも mise 非提供なら保持し、理由を表示する。vendor ディレクトリは見出しの binary 以外も持つため (Neovim の bin は `tee` / `xxd` / `win32yank` も含む)、名前の一致だけで判断しない。
- 変更は Machine PATH のみ。User PATH、インストール済みプログラム、ディレクトリは消さない。除去後も vendor コピーはディスクに残るため、entry を戻せば元の解決順に戻る。
- 書き込み前に展開前の生値を保存し、`-Restore` で復元できる。管理者権限が無い場合 `-Apply` は変更しない。
- 既定は plan のみ (書き込みなし)。

保持対象 (除去しない) の例と理由:

- `coreutils\bin`、chocolatey の `bin`、`nodejs\`: mise が提供しないコマンド (`corepack`, `choco`, `sops`, `terraform` など) を含む。これらは各 installer のアンインストールで解消する。
- `%APPDATA%\npm`、`%USERPROFILE%\.bun\bin`: 他の npm / bun global package と同居しており、PATH entry の削除では解消できない。
- `WindowsApps` / `WinGet\Links`: GUI アプリと vendor updater が使う。`mise` 本体もここから解決される。

### 宣言済みツールを実行して確認する

`verify.ps1` は `Get-Command` による解決に加えて、宣言済みツールを実際に起動する。失敗時は mise key、実行したコマンド、終了コード、出力の先頭を報告し、修復を `mise install <key> --force` として示す。

存在確認だけでは、インストール済みと報告されながら実行時に落ちる状態を見逃すため。

### 旧 Rust home は削除する

ADR-0021 の「残す」判断を更新する。新 home が自立していること (rustc / cargo / 全 `cargo:` tool)、旧 home が PATH と config から参照されないことを確認し、バックアップを取得した上で削除する。`verify.ps1` は旧 home が再び現れた場合に WARN で報告する (FAIL にはしない)。

## Consequences

- activation 無しの経路 (`pwsh -NoProfile`、Scheduled Task、IDE、GUI 起動) でも、宣言済みツールは mise に解決される。`mise exec --` や shim の絶対パスに依存しない。
- Machine PATH の変更は新規プロセスにのみ効く。既に起動済みの shell は古い PATH を保持するため、除去したコピーを解決しようとして失敗することがある。`-Apply` 後は新しいターミナルを開く。
- 管理者権限が無い環境では PATH の一本化は完了しない。`verify.ps1` はその状態を FAIL として報告し続ける。
- 壊れた install は `mise install` では直らない。修復操作が `--force` であることが README と verify のメッセージに明示される。
- mise が提供しないコマンドを持つ vendor ディレクトリは残る。完全な一本化には各 installer でのアンインストールが必要で、それは PATH の整理とは別の操作として扱う。

## Re-evaluate

- mise が Machine PATH 相当の配置 (system shims) を Windows で標準提供するようになった場合
- mise の npm backend が内部依存を install dir の外に hoist する実装へ変わった場合
- `mise install` が壊れた install を検出して自動修復するようになった場合
