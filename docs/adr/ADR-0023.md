# ADR-0023: Vercel CLI は machine-global baseline に含めない

- Status: Accepted
- Date: 2026-11-13
- Extends: ADR-0006
- Related: ADR-0007, ADR-0010

## Context

`mise.global.toml` は Vercel CLI を `vercel = { version = "latest", depends = ["node"] }` として machine-global baseline に宣言していた。ADR-0006 の baseline 一覧にも Supabase CLI と並んで記載されていた。

2026-11-13、この宣言が `mise upgrade` と continuous update train の両方を停止させていることが判明した。失敗はネットワークでも version 解決でもなく、mise の embedded npm backend (`aube`) が既定で有効にしている supply-chain trust gate である。

```text
aube install failed: failed to resolve dependencies
  caused by: trust downgrade for @vercel/cli-config@0.3.8 (trustPolicy=no-downgrade):
  earlier published version 0.1.1 had trusted publisher but this version has no trust evidence
```

`trustPolicy=no-downgrade` は「同一 package の過去 release より trust evidence が弱い version」を拒否する。`@vercel/*` は古い release が Sigstore provenance を持ち、現行系列は trusted-publisher metadata のみのため、tier 降格と判定される。

実測では vercel 65.0.0〜65.14.0 のすべてが解決不能で、除外には 39 個の `@vercel/*` package/version が必要だった。Vercel が release するたびに増えるため、version 単位の除外リストは維持できない。

検討した選択肢:

- `@vercel/*` を一括除外する
- `npm.shell_out` / `npm.package_manager = "npm"` で npm CLI へ切り替える
- vercel を baseline から外す

前二者は npm backend の検証境界を Vercel の依存グラフ全体・将来の version まで広げて無効化する。ADR-0007 が Open Code Review で同じ判断をしている。vercel は npm 以外の公式配布経路 (standalone binary を持つ GitHub Release) が無く、ADR-0007 の「公式 GitHub Release へ移す」解決も取れない。

## Decision

Vercel CLI を `mise.global.toml` の machine-global baseline から外す。

- `trust_policy_excludes` を追加しない。npm backend の trust policy は全 tool で既定のままとする。
- `npm.shell_out` / `npm.package_manager` を変更しない。trust 検証を迂回する経路を導入しない。
- Vercel CLI が必要なマシンでは project 側で管理する。machine-global の baseline に戻さない。
- 各 platform README、verify script、NixOS flake の tool 一覧からも vercel を除去し、宣言と検証を一致させる。

併せて、この失敗を CI が検出できなかった gap を塞ぐ。

- CI の continuous update resolution 検証は `--dry-run` をやめ、update train と同じ実解決を分離された `MISE_CONFIG_DIR` で実行する。`--dry-run` は npm 依存解決を行わないため、train が赤でも CI は緑になっていた。
- `mise.global.lock` が宣言に無い supply-chain policy option を保持していないか検査する small script を CI に入れる。`mise lock` は config から消えた option を lock に残すため、宣言変更だけでは乖離が解消しない。

## Consequences

### Positive

- `mise upgrade` と continuous update train が再び収束する
- 検証境界を一切緩めずに済む。他の npm tool は trusted-publisher / provenance 検証を維持する
- 宣言と lock の乖離を CI が検出する
- update train の失敗を CI が事前に検出する

### Trade-offs

- Vercel CLI は portable baseline の対象外になり、マシンごと・project ごとに導入判断が必要になる
- Vercel の npm 公開が provenance を一貫して持つようになれば、baseline 復帰は再検討できる

## Verification

- `mise lock --global --bump --platform linux-x64,windows-x64,macos-x64,macos-arm64` が exit 0
- `mise.global.lock` に `tools.vercel` が存在しない
- `python3 scripts/check-mise-policy-sync.py .` が成功
- `./scripts/ci.sh` が成功

## Re-evaluate

- Vercel の npm 公開が trusted-publisher / provenance を一貫して持ち、`trustPolicy=no-downgrade` を通るようになった場合
- Vercel CLI が standalone binary を公式 GitHub Release で配布するようになった場合
- 日常的に使う machine-global CLI としての需要が戻った場合
