# ADR-0003: NixOS Uses a Declarative Stable-System / Unstable-Tooling Profile

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0001, ADR-0002
- Superseded by: None

## Context

NixOS can reproduce most of the development environment without imperative curl installers or mutable global package managers.

At the same time, two different freshness requirements exist:

- the operating-system baseline should prioritize predictable upgrades and rollback
- fast-moving developer tools such as Claude Code, OpenCode, Worktrunk, Bun, and the Rust toolchain benefit from fresher package revisions

As of the investigation date, NixOS 26.05 is the current stable NixOS release. Home Manager provides a matching `release-26.05` branch. Current nixpkgs also contains first-class packages for `claude-code`, `opencode`, and `worktrunk`.

Using upstream installers for those tools on NixOS would bypass the declarative package graph, make rollback incomplete, and duplicate state outside the Nix configuration.

A full machine configuration cannot be universal: hardware configuration, boot loader, disk layout, hostname, local user identity, and the original `system.stateVersion` / `home.stateVersion` belong to a concrete host.

## Decision

### 1. NixOS is managed as a declarative reusable profile

`platforms/nixos` is a Flake-based reusable profile.

It exports:

- a NixOS system module for Nix-level defaults
- a Home Manager module for the user development environment
- an overlay exposing a separate unstable package set
- a helper for composing a host configuration without embedding hardware-specific state in the reusable profile

The Nix configuration is the bootstrap mechanism for this platform. Do not reproduce the Ubuntu/WSL imperative installer model on NixOS.

The canonical fresh-machine entrypoint is the Flake default app:

```bash
nix run 'github:rebuildup/pc-setup?dir=platforms/nixos'
```

The app carries its bootstrap runtime dependencies through Nix and hands off to the dotfiles bootstrap. A default `devShell` exists only as a manual/debug fallback. Users should not have to remember or maintain a package list for bootstrap.

### 2. System baseline tracks NixOS 26.05 stable

The primary `nixpkgs` input tracks:

```text
github:NixOS/nixpkgs/nixos-26.05
```

Home Manager tracks the matching:

```text
github:nix-community/home-manager/release-26.05
```

The Home Manager input follows the stable `nixpkgs` input.

A future stable NixOS release requires an explicit update of these inputs and review of release notes before changing the baseline.

### 3. Fast-moving development tools use a separate unstable package set

A second input tracks:

```text
github:NixOS/nixpkgs/nixos-unstable
```

The reusable overlay exposes this as `pkgs.pcSetupUnstable`.

The initial unstable-tool set is:

- `claude-code`
- `opencode`
- `worktrunk`
- `infisical`
- `bun`
- Rust compiler/tooling where a materially fresher stable toolchain is desirable

The rest of the baseline CLI/build environment remains on the stable package set unless there is a concrete freshness reason to move it.

This split keeps the OS base conservative without forcing rapidly moving agent/developer tooling to lag behind stable nixpkgs.

### 4. Nixpkgs packages are preferred over vendor installers on NixOS

When a required tool is available and maintained in nixpkgs, install it through the Nix package graph.

For the initial profile this means:

- Claude Code: `pkgs.pcSetupUnstable.claude-code`
- OpenCode: `pkgs.pcSetupUnstable.opencode`
- Worktrunk: `pkgs.pcSetupUnstable.worktrunk`
- Infisical CLI: `pkgs.pcSetupUnstable.infisical`
- Bun: `pkgs.pcSetupUnstable.bun`

Do not run the Claude Code, OpenCode, Bun, Cargo, or similar self-installers as part of normal NixOS provisioning for these tools.

If a package disappears, becomes materially stale/broken, or diverges from required upstream behavior, revisit this decision rather than silently adding an unmanaged installer.

### 5. Home Manager owns the user development profile

User-level development packages and shell integration are defined through Home Manager.

Worktrunk Bash integration is declarative:

```bash
eval "$(wt config shell init bash)"
```

Do not use `wt config shell install` as the canonical NixOS setup path because it mutates shell configuration outside Home Manager.

Authentication remains interactive and outside Nix-managed files.

### 6. Host identity and compatibility state remain host-specific

The reusable profile MUST NOT choose:

- disk partitioning or filesystems
- boot loader
- `hardware-configuration.nix`
- hostname
- user password
- SSH private keys
- API/provider credentials
- `system.stateVersion`
- `home.stateVersion`

A concrete host configuration imports this profile and supplies those values.

The `stateVersion` values are lifecycle compatibility markers and must remain the values from the host's original installation unless their respective migration guidance is deliberately followed.

### 7. Secrets do not enter the Nix store

Flake inputs, Nix expressions, generated store paths, and committed Home Manager files are not secret storage.

Provider credentials, tokens, cookies, private keys, and other secrets remain outside this repository.

For the personal development baseline, Infisical is the central secret source of truth. The NixOS profile installs the Infisical CLI but does not place Infisical session credentials or secret values in the Nix store. Local human access is interactive; automation uses dedicated machine identities and should prefer short-lived platform/OIDC authentication where available.

### 8. Flake locking is part of concrete reproducibility

A concrete host should commit its `flake.lock`.

The reusable profile declares update channels; the lock file selects the exact revisions used by a host generation.

Update flow should be explicit:

```bash
nix flake update
sudo nixos-rebuild test --flake <host-flake>#<host>
sudo nixos-rebuild switch --flake <host-flake>#<host>
```

Use `test` before `switch` when changing the system profile.

## Consequences

### Positive

- development packages become part of the same declarative graph as the NixOS environment
- rollback includes developer tooling instead of leaving mutable installer state behind
- stable OS packages and fast-moving tooling can advance at different cadences
- Worktrunk shell integration no longer needs to mutate `.bashrc`
- hardware- and user-specific compatibility state is not accidentally generalized

### Trade-offs

- the configuration uses two nixpkgs revisions
- mixing stable and unstable packages increases evaluation/download surface
- updates require Nix evaluation and a deliberate rebuild instead of tool self-updaters
- a reusable profile alone cannot install a complete physical NixOS host without hardware/boot configuration

## Verification

Repository validation should cover:

- Nix syntax for committed `.nix` files
- Flake evaluation where CI capability is available
- shell validation for verification scripts
- real-host verification with `platforms/nixos/verify.sh`

A green repository CI run does not prove hardware bootability or account authentication.

## Re-evaluation triggers

Re-evaluate this decision when:

- the supported NixOS stable release changes
- Home Manager changes its release compatibility model
- one package set can satisfy both system stability and tooling freshness without meaningful trade-off
- Claude Code, OpenCode, Worktrunk, Infisical, Bun, or Rust packages become unusable/stale in nixpkgs
- an actual NixOS host is added and exposes requirements that the reusable profile cannot represent cleanly
- a different declarative Nix architecture provides stronger reproducibility with less complexity
