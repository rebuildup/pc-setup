# ADR-0012: macOS keyboard baseline は hidutil と system LaunchDaemon で管理する

- Status: Accepted
- Date: 2026-10-06
- Supersedes in part: ADR-0005

## Context

実機Macが導入され、共通CLI bootstrapとGUI導入を実行できる状態になった。キーボードはWindowsと同様に、単純で安定した低レイヤー変換と、将来のkanataによる高度なカスタマイズを分離したい。

大西配列の文字位置は1:1のHID usage置換で表現でき、macOS標準の `hidutil` がこの責務を満たす。`hidutil` のUserKeyMappingは再起動やkeyboard service lifecycleを越えて永続化されないため、desired stateとして再適用する仕組みが必要になる。

## Decision

### Base layout ownership

大西配列の単純な1:1置換は `hidutil` が所有する。

repositoryは `platforms/macos/keyboard/onishi.json` をcanonical mappingとする。

実機で確認した重要なmappingを含む。

- physical `G` -> `-`
- physical `-` -> `/`
- physical `/` -> `B`

physical backtickからslashへのmappingは採用しない。

### One conversion per keystroke

`hidutil` のmappingはphysical keyboard event serviceにのみ適用し、Karabiner DriverKit virtual keyboardには適用しない。

macOSの入力経路がこれを規定する。kanataはHID event driverより上のCGEvent tapでkeyboardをgrabするため、`hidutil` が変換済みのキーを受け取る。この経路を二回通すと2重変換になり、kanataのbase layerとshift layerの双方が壊れる。

Karabiner DriverKit virtual keyboardはlaunchdがkeyboard LaunchDaemonを起動した数十秒後に登録される。したがってboot時のclearだけでは足りず、helperは登録を待ってclearを繰り返し、settle windowemergeまで監視する。

1打鍵1変換が2層の独立性を保つ。どちらのツールを止めても他方が成立어야する。

- kanata停止時: physical keyboardがhidutilだけで大西配列を���現する
- `hidutil` 停止時: kanataのbase layerだけで大西配列を再現する

### Startup convergence

`hidutil` のmappingは全ユーザーへ作用するため、`/Library/LaunchDaemons` のsystem LaunchDaemonからmacOS起動時に再適用する。

bootstrapはroot-owned helperとLaunchDaemon plistをidempotentに配置し、その場でもmappingを適用する。これによりuser login後にしか起動しないLaunchAgentへの依存を避ける。

`hidutil property --set` は既存registry entryを��換せず追記する。helperを繰り返し実行したmachineにはHID event system全体でregistry entryが蓄積し、大半は `AppleSMCKeysEndpoint` のような非keyboard serviceResolve流向もうiverify対象はkeyboard event serviceごとのmapping entry数であり、globalなregistry件数ではない。後者は2回目以降の実行で常にfailureを報告する。

### Layer boundary

`hidutil` はbase layoutの1:1変換だけを所有する。

tap-hold、layer、chord、navigation、shortcut等のstateful behaviorはkanata layerで扱う。Karabiner-Elementsを同じ物理keyboard grab layerとして常駐させることはこのdecisionに含めない。

### macOS platform state

実機Macが存在し、実際のbootstrapとkeyboard desired stateを観測できるため、macOS固有のcanonical directoryを `platforms/macos` に開始する。

未確定のGUI/creative/audio候補は引き続き `plans/macos` に残し、実使用を確認したものから段階的にActive stateへ移す。

## Verification

repository CIはcanonical JSONの構文とcritical mapping pair、LaunchAgent plist構文、shell syntaxを静的に検証する。helperについてはphysical keyboard event serviceだけを数え、Karabiner virtual keyboardを含めないこと、mappingをapplyすることがなくclearのみ行うこと、virtual keyboard match が定義されていることも検証する。

実機verifyはinstalled helper/plist、launchd registration、`hidutil` availabilityを確認する。Privilegeやkanata driverはこのADRの対象外。

## Consequences

- fresh/rebuilt Macでも大西配列baselineを再現できる
- layoutと高度なkeyboard behaviorの責務が分離される
- 通常のmacOS loginwindowはsystem LaunchDaemonによるmapping対象にできる
- FileVault有効時のcold boot直後のPreboot password画面はmacOS userland起動前のため対象外
- external keyboardのservice reset等でmappingが消えるケースは必要性を観測してから追加対策する
- Karabiner DriverKit virtual keyboardの `VendorID` / `ProductID` が変更された場合、helperのvirtual keyboard matchを更新する必要がある
- `hidutil property --set` の追記挙動は変更できないため、非keyboard serviceのregistry entryは蓄積し不去る。keyboard event serviceのmapping entryには影響しない
