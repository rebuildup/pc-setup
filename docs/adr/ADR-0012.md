# ADR-0012: Promote Observed macOS Capabilities Incrementally

- Status: Accepted
- Date: 2026-10-06
- Supersedes: ADR-0005

## Context

A real Mac is now available and the root mise-based bootstrap has completed on that machine. The previous macOS ADR intentionally kept all macOS state under `plans/macos/` until an actual machine could be observed.

The first platform-specific capability confirmed from actual use is keyboard input. The user uses the Onishi layout for the base 1:1 key arrangement and intends to layer kanata on top for higher-level behavior.

Waiting for every GUI, creative, audio, and peripheral candidate to be accepted or rejected before any observed macOS state can become canonical would now prevent pc-setup from representing the real machine accurately.

## Decision

### 1. macOS may be promoted incrementally from observed state

`platforms/macos/` holds capabilities that have been observed and explicitly adopted on the actual Mac.

Unresolved application candidates may remain under `plans/macos/`. Their presence there does not make them desired state, and Windows inventory is still not inherited automatically.

### 2. Base Onishi layout uses macOS hidutil

The simple physical-key-to-key mapping is owned by the macOS `hidutil` mechanism.

The confirmed mapping includes:

- physical `-` -> `/`
- physical `G` -> `-`
- physical `/` -> `B`

The backtick key is not remapped to slash.

This layer contains only stable 1:1 remapping. Layers, tap-hold behavior, chords, navigation, and other stateful input behavior belong to kanata and are outside this decision.

### 3. A user LaunchAgent reapplies the mapping at login

Apple documents that `hidutil` remappings are lost after restart or keyboard-service removal. pc-setup therefore installs a user LaunchAgent that executes the repository-managed mapping when the user session starts.

The LaunchAgent is preferred over a privileged system LaunchDaemon for this baseline because `hidutil` itself requires no special privilege and the desired behavior only needs to be guaranteed for the interactive development session.

The setup is idempotent: rerunning bootstrap replaces the installed helper and plist with the current repository versions, reloads the job, and reapplies the mapping.

### 4. Pre-login remapping is not required

The macOS login screen may remain on the system keyboard layout. The desired invariant begins with the user's graphical login session.

If a future requirement needs remapping before user login, that is a separate decision because it introduces a privileged daemon and a different authorization/update boundary.

## Consequences

- the actual Mac now has an active platform directory without pretending unresolved app candidates are adopted
- the Onishi base layer no longer depends on manually rerunning a command after reboot
- kanata can remain focused on dynamic/high-level remapping
- bootstrap stays unprivileged for this keyboard layer
- external keyboard/service lifecycle behavior can be refined later if actual use shows that login-time application is insufficient

## Re-evaluation triggers

Re-evaluate when:

- kanata is adopted on macOS and its event-grab ordering conflicts with `hidutil`
- a keyboard must be remapped before graphical login
- keyboard hot-plug causes the active mapping to disappear during normal use
- Apple changes `hidutil` or LaunchAgent behavior materially
