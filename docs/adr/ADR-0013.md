# ADR-0013: macOS のコンテナ実行環境は Colima と Homebrew Docker CLI で管理する

- Status: Accepted
- Date: 2026-10-08
- Related: ADR-0005, ADR-0006

## Context

実機 Mac で Docker Desktop を利用していたが、アンインストールした。この repository の主な consumer は Codex / Claude Code / Pi などのコーディングエージェントであり、GUI と常駐サービスは要件ではない。代わりに Apple Virtualization.framework 上の仮想機として Colima を採用し、Homebrew の `docker` / `docker-compose` / `docker-buildx` を CLI として使う。

パッケージ導入は mise が担う (ADR-0006)。ただし `mise.global.toml` は Windows / macOS / Linux が共有する machine-wide config であり、そこに `[bootstrap.packages]` を追加すると OS 条件がないかぎり全 OS に適用される。加えて Homebrew の prefix は Apple Silicon と Intel で異なり、Docker Desktop が残した path や context にも依存したくない。

## Decision

### Container runtime

macOS のコンテナ実行は Colima が所有する。desired な VM 形状は次のとおりで、arch は host に追従する。

```text
runtime: docker / vm-type: vz / mount-type: virtiofs
cpus: 4 / memory: 4GiB / disk: 60GiB
```

Docker Desktop は導入しない。`mise.global.toml` が `docker-desktop` cask を宣言されていないことを CI で確認する。

### Package scope

macOS 専用パッケージは `mise.global.toml` の `[bootstrap.packages]` に `os = "macos"` 付きで保持する。ファイルを OS ごとに分割せず、同一ファイル内で OS 条件によって分離する。CI は TOML 上の条件と、mise が実際に解決する集合の一致を検証する。`[tools]` は portable CLI layer であり、system package をそこに置かない。

Colima の初期化は `platforms/macos/containers/install.sh` が担う。これは VM が存在しないときだけ作成し、既存 VM は削除・再作成・サイズ変更をしない。設定差分は報告のみで、変更するかどうかは人が決める。データ破壊を伴う操作は script から行わない。

### Docker CLI plugins

`docker compose` / `docker buildx` は `~/.docker/cli-plugins` への symlink で Docker CLI に認識させる。Homebrew の formula root は `mise bootstrap packages where` に問い合わせ、解決できなければ PATH と `HOMEBREW_PREFIX` を辿る。`/opt/homebrew` のような prefix を前提にしない。

リンクは既存のものを尊重する。正常な symlink と他人の実体ファイルは残し、壊れた symlink だけを張り替える。

### Registry credentials

`brew:docker-credential-helper` を macOS 専用パッケージとして宣言する。Docker Desktop は `docker-credential-osxkeychain` を同梱し、アンインストールでその binary を消しても `~/.docker/config.json` の `credsStore` は残す。残った `credsStore` は helper を起動できないため、以降の `docker pull` は credential 取得で失敗する。同じ Keychain backed helper を Homebrew から持ってくることで、Docker Desktop の残骸と plaintext な credential 保存の両方を避ける。

### Docker Context

Docker Context は `colima` を使う。`DOCKER_HOST` をグローバルに固定しない。shell 起動ごとに別の daemon を指す状態は解消が難しく、context が持つべき情報と重複する。script は既存の context を切り替えず、切り替えは明示的な手動作業とする。

### Lifecycle

Colima は常時起動を前提にしない。起動・停止・状態確認は `platforms/macos/containers/control.sh` が提供し、launchd の常駐 service は作らない。verify は VM を起動せず、停止中は「作成済みだが停止中」と未構築を区別して報告する。

## Verification

- `platforms/macos/containers/verify.sh`: mise 設定の読み込み、宣言された macOS パッケージの active 状態、`colima` / `docker` / compose / buildx / `ffmpeg`、Docker Context、VM の runtime / arch / サイズ / vmType / mountType、daemon 接続。`--smoke` で明示的に container を1回実行できる
- `scripts/ci.sh`: shell 構文と ShellCheck、TOML 構文、`[bootstrap.packages]` の `os = "macos"` 条件、Docker Desktop の不在、script 契約 (prefix の非ハードコード、`colima delete` / `DOCKER_HOST` export / `docker context use` の不在、verify が VM を起動しないこと)、mise がこの host で解決する package 集合と宣言の一致

## Consequences

### Positive

- Docker Desktop なしで、エージェントが通常の `docker` コマンドを context 経由で使える
- 他 OS の bootstrap に Homebrew cask / formula が漏れない
- 既存 VM のデータは script から触られない
- Homebrew prefix に依存しないため、Apple Silicon と Intel で同じ手順が動く

### Trade-offs

- Kubernetes や GPU を使う場合は追加設定が必要になる
- VM の作成には仮想機イメージの取得が必要で、初回 bootstrap は重い
- 既存 VM の設定差分は自動修正されないので、変更は人が行う

## Re-evaluation triggers

- Apple Virtualization.framework が使えない構成が対象に入った場合
- Kubernetes / GPU / 複数 profile が regular requirement になった場合
- Docker Desktop の導入が組織契約などによって避けられなくなった場合
- mise の `[bootstrap.packages]` の OS 条件の意味が変わった場合
