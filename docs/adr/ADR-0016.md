# ADR-0016: 採用（train）・配備（converge）・シェル（activate のみ）の責務を分離し、OS スケジューラで main を配備する

- Status: Accepted（macOS 実装。WSL2 / Windows のスケジューラは未実装）
- Date: 2026-11-05
- Extends: ADR-0010, ADR-0006
- Related: Issue #160

## Context

2026-11-04 の実機調査で、3 環境すべてで「更新がシェル起動に依存する」「配備元が作業チェックアウトに結びつく」ことを確認した。

- macOS: `~/.config/mise/config.toml` と `mise.lock` は `~/src/pc-setup/` を指す symlink で、そのチェックアウトは dirty な作業ブランチ `local/p153-global-mise` にある。update 系の cron・LaunchAgent はない。
- 更新の採用は ADR-0010 の update train が担うが、端末側の配備は誰も定期的に行っていない。mise の `activate` はシェル起動時にしか効かない。
- 古い実行中プロセスが旧バイナリを保持している（macOS で claude 2.1.302 / 2.1.316 が稼働中。mise の current は 2.1.317）。旧セッションを検出する仕組みはない。

採用（何を入れるか）と配備（端末をそれに合わせる）が別の経路で、どちらも作業チェックアウトの状態に左右されていた。

## Decision

### 1. 責務の分離

| 層 | 持ち主 | 内容 | 禁止事項 |
| --- | --- | --- | --- |
| 採用（adoption） | GitHub Actions update train（ADR-0010） | `mise lock --global --bump` で `mise.global.lock` と `.mise/locks/` を更新し、CI 検証後に main へ merge する | 端末側での解決 |
| 配備（deployment） | `scripts/converge.sh`（OS スケジューラから定期実行） | 配備用チェックアウトを main に ff-only で追従させ、コミット済みの採用状態を `mise install --locked` で端末に反映する | `mise upgrade`、`mise lock`、`latest` の解決 |
| シェル | `mise activate`（`.zshrc` など） | PATH と環境変数を整えるだけ | 更新、配備、採用の処理 |

converge は採用の状態を変えない。採用済みの lock を消費するだけである。ADR-0010 §5 の「locked mode で install する」をそのまま端末側の定期処理にしたものになる。

### 2. 配備用チェックアウトの場所

`~/.local/share/pc-setup/deploy`（`PC_SETUP_DEPLOY_DIR` で上書き可）を single-branch・`origin/main`・ff-only で保つ。

- 作業チェックアウト（`~/src/pc-setup` など）は配備に使わない。作業ブランチが何であっても、配備される内容は main に限定される。
- `~/.local/libexec/pc-setup` は実行ファイルや補助バイナリの置き場として使われてきた。チェックアウト（ソースツリー）を置くとバイナリ置き場と混ざるため使わない。
- `~/.local/state/pc-setup` は状態・ログ・ロックの置き場にする。ソースツリーは置かない。
- `apply-global-mise.sh` は自身の位置から repo root を決めるため、converge は必ず `$DEPLOY/scripts/apply-global-mise.sh` を呼ぶ。これで `~/.config/mise/config.toml` と `mise.lock` は配備用チェックアウトを指す。

### 3. 安全性

- **dirty は拒否してスキップ**：配備用チェックアウト、または `~/.dotfiles` に未コミットの変更があるとき、reset、checkout、stash はしない。そのステップを skipped として記録し、status の errors に載せる。`~/.dotfiles` については既存の `sync-dotfiles.sh` の拒否をそのまま使う。
- **配備用チェックアウトが main 以外、または origin が想定外なら error**：どちらも自動で直さない。
- **冪等**：2 回目の実行は変更なしで exit 0 になる。
- **同時実行ガード**：`~/.local/state/pc-setup/converge.lock/` を mkdir で取る（macOS に flock はない）。pid を書き、pid が死んでいれば stale として退ける。退ける時は rename してから削除し、別プロセスが新しく取った lock を消さないようにする。
- **再実行の境界**：同期後に配備済みの `converge.sh` へ `exec` する。bash はスクリプトを逐次読むため、実行中に自分の本体が差し替わると壊れる。`exec` は pid を保つので、同じ lock を引き継げる。
- **巻き戻しをしない理由**：`apply-global-mise.sh` が config のリンクを張り替えた後で install が失敗しても、ロールバックはしない。mise の install は追加的で、旧バージョンはディスクに残る。巻き戻すと、この処理が取り除こうとしている dirty な作業チェックアウトへのリンクが戻ってしまう。欠けているツールは status に載るので、次の実行で再試行される。
- **終了コード**：0 は全ステップ成功、1 は失敗あり、3 は skipped または pending あり、75 は lock 競合。

### 4. スケジューラ：macOS LaunchAgent（StartInterval 3600、RunAtLoad）

- **LaunchAgent（ユーザ単位）**：mise のインストール先、`~/.config`、ログイン keychain（gh の認証）は全てユーザ領域にあるため、root の LaunchDaemon にすると権限と所有者が合わなくなる。
- **StartInterval**：converge は冪等で軽く、固定の周期で十分である。カレンダー時刻に縛ると「その時刻に Mac が起きていなければ実行されない」ことになる。RunAtLoad は再ログイン直後の反映を担う。
- **シェル再起動なし**：LaunchAgent は OS 側で起動するので、ターミナルを開き直さなくても反映される。mise の shim と PATH の更新は、次のプロンプトか `hash -r` で既存シェルにも届く。既に動いているプロセスは旧バイナリのまま残る（後述の stale 検出の対象）。
- 導入は `platforms/macos/install-converge.sh`。冪等で、`--uninstall` で取り除ける。既存の `dev.rebuildup.pc-setup.devnode.*` は一切触らない。
- 3600 秒は仮の値である。sleep 中の発火、復帰後の追いつき実行は実機で観測しておらず、仮定していない。

### 5. 状態レポート：`~/.local/state/pc-setup/status.json`

converge の終了時（成功・失敗とも）に `scripts/converge-status.sh --write` が書く。内容：

- 配備された pc-setup と dotfiles の revision（HEAD sha、branch、dirty）
- `mise.config_target`（リンク先のパス）と `mise outdated` の行数
- verify の結果と時刻
- 最後の converge の開始、終了、終了コード、各ステップの結果
- stale なプロセス一覧（pid、バイナリ、現在の期待パス）。検出のみで、シグナルは送らない
- 未解決エラーの文字列

記録しないもの：環境変数の値、トークン、鍵、プロセスの引数。バイナリのパスは含むが、引数は含まない。`--print` で人が読める形に整形する。

**他の端末から読む方法**：中央デーモンは置かない。herdr や ssh で対象端末の `status.json` を読むことで、環境をまたいだ一覧にする。

### 6. Stale セッションの検出

`ps` で mise の install 配下（`~/.local/share/mise/installs/<tool>/<ver>/`）から起動されたプロセスを列挙し、`mise where <tool>` が返す current と比べる。違えば stale として報告する。tool 名がディレクトリ名から一意に決まらないもの（npm パッケージなど）は unresolved として別に報告し、stale とは判定しない。

### 7. アプリの自己更新との関係（ADR-0010 §6）

ADR-0010 §6 は、公式の制御がある場合にだけ vendor の自己更新を止めてよいとしている。出力のフィルタや正規表現による抑制は使わない。

- **claude**：mise が `latest` で管理している。Claude Code 自身も自己更新する。`DISABLE_AUTOUPDATER` が公式の制御として確認できなかった（[anthropics/claude-code#10079](https://github.com/anthropics/claude-code/issues/10079) など、動かないという報告がある）ため、この PR では設定しない。公式の設定キーを確認してから別 PR で扱う。
- **pi**：`pi update` の通知が出る。Web 検索の結果では、環境変数 `PI_SKIP_VERSION_CHECK=1`（版チェックのみ停止）と `PI_OFFLINE=1`（起動時のネットワーク処理すべてを停止）、設定ファイル（`~/.pi/agent/settings.json`）が挙がった。ただし、これらは検索スニペットでのみ確認したもので、ページ本体は開いていない。インストール済みの `@earendil-works/pi-coding-agent` 同梱ドキュメントでも `selfUpdateCommand` は見つからなかった。キー名を確認するまでは採用しない。
- いずれも `mise.global.toml` は変更しない（採用ポリシーの変更になるため、別の変更として扱う）。

### 8. 既知の注意：`npm:@deepseek-ai/dsh`

dsh は未マージの PR #154 にしか宣言がない。配備先が main に切り替わると、dsh の宣言が消える。converge は、直前のリンク先に宣言があり main に無い場合、`dsh-declaration` を pending として記録し、status の errors に「PR #154 待ち」と載せる。宣言そのものは追加しない。

## Consequences

- 採用と配備が別の経路になり、作業ブランチの状態が配備に影響しなくなる。
- macOS では、ターミナルを開かなくても定期的に main へ追従する。
- 失敗は status に残り、次の実行で再試行される。
- 旧バイナリを保持する古いプロセスは検出されるが、止めはしない。止めるかどうかは人が決める。
- `apply-global-mise.sh` の config 張り替えは `rm` の後に `ln -s` を行うため、ごく短い間は config が存在しない。converge の側ではこの窓を塞げない。別途改善が必要である。
- WSL2 と Windows のスケジューラは未実装。ADR の方針（採用は train、配備は converge、シェルは activate のみ）は両 OS に適用する。

## Re-evaluation triggers

- mise の locked install、または global config の解決の仕様が変わったとき
- 定期実行で足りず、イベント駆動の配備が必要になったとき
- pi や claude が公式の自己更新制御を提供したとき（§7 を更新する）
- macOS の launchd が StartInterval の sleep 中の挙動を変えたとき（§4 の観測で確かめる）
