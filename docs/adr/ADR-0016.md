# ADR-0016: 新規WSL workerをWindows標準ユーザーごとに分離する

- Status: Accepted
- Date: 2026-10-25
- Decision authority: [Issue #134](https://github.com/rebuildup/pc-setup/issues/134) のユーザー選択

## Context

同じWindowsアカウント内でdistro名・Linux UID・node IDを分けるだけでは、rwのWindows mountやinterop経由の管理鍵アクセスを防げない。PATH上のWindows shimもLinux runtimeの存在証明にはならない。

## Decision

相互に権限を分離する新規workerは、論理instance UUIDごとに新規の標準Windowsローカルユーザーと、そのuserに属するWSLを持つ。SID・ユーザー名・distro名・保存pathはUUIDに結び付けた非秘密resource属性であり、論理identityの代替にしない。既存basic/Ubuntuは変更しない。

OS層はpc-setupが所有する。manifestと固定probeはAdministrators/SYSTEMだけが変更でき、workerにはReadAndExecuteだけを与える。dataは当該SIDだけにModifyを与え、他worker/Users全体へ許可しない。local Users以外のgroup所属、foreign/partial stateの採用、既存password reset、privileged group追加、既存profile/SSHの修復は禁止する。

manifestのOwner namespaceとOS APIのDescriptionは別属性にする。AccountDescriptionは `pcw/v1/<完全UUID>` の43文字で、Windowsの48文字制約に収める。作成と照合はこのplan属性へ統一し、旧Description/属性欠落は無断で移行・adoptしない。

native Windowsのcredentialed process creationを.NETのUserName/Password(SecureString)/LoadUserProfileで使用する。broker/daemonを導入しない。環境はallowlistから作り、管理者token・controller PATH/資格情報/canaryを渡さない。password保管・配送は統合側との別gateで、argv・ログ・manifest・平文ファイルへ保存しない。

公式Canonicalのfresh imageと独立確認したSHA256を入力する。既存distro export/device鍵/login/cacheをコピーしない。URL許可とhash一致だけでは由来を証明できず、operatorが公式releaseのchecksum署名・出所を先に確認する。

## Evidence and limits

pure contract・scratch ACL/state fixture・現在tokenの環境probeは別ユーザーの実機分離proofではない。後段でnative profile/logon、管理鍵と別worker領域のアクセス拒否、canary非継承を実測する。鍵はhandle open/closeだけで判定し、内容は読まない。

管理者Verifyはmanifest/account/ACL/hashを検査する。worker HKCUは未ロードの場合があるため、distro inventoryはcredentialed childで検査し、Verify単独で不存在を主張しない。registry不存在のみ空とし、アクセスエラーや不正登録は拒否する。profile設定はinventory検査後だけ。

`.wslconfig`は資源予算であり、workerが変更不能なhard quotaではない。別Windows userのWSL VM/network/hostサービス共有とlimitsの実効性は別途実測する。host administratorからの隔離や敵対kernel/VM境界は保証しない。その境界が必要なら専用VM等を再評価する。

## Re-evaluate

native profile/process非対応、host秘密/他workerへの到達、limits不適用があれば、認証緩和や管理者fallbackではなく機構を再設計する。

2026-10-26のWSL接続継続要求に対応し、既存manifest/probeを変更しない別の管理者所有stageから、当該標準userのnative NoProfile processでUUID対応distroの新規importを行う。既存登録やinstall pathがある場合はimportを拒否し、source/ACL/hash driftや部分状態をadoptしない。専用imageは管理者だけが書けるstageに置き、workerは読取だけとする。registry検査はworker HKCUで実行し、import成功とLinux起動・SSH・Herdr到達の証拠を分ける。unregister/global shutdown/既存Ubuntu変更は提供しない。

専用distroのOS package baselineは、別の `maintenance-v1` stageに固定されたSHA256照合済みsourceだけで適用する。controllerはレビュー済みclean commitを要求し、正確なworker SIDのnative processから、UUID対応distroの `wsl.exe --user root` へ固定scriptをstdinで渡す。root scriptはUbuntu 24.04の `mise.toml` にあるLinux APT baselineのみを対象に、`apt-get update` 後のsimulationで既存packageのupgrade/removalを検出したら停止し、許容planだけ `apt-get install --no-upgrade` で適用する。full upgrade/removal、sudo権限付与、mise/dotfiles/bootstrapやuser-writable scriptのroot実行は行わない。実行前後のpackage inventoryを照合し、raw APT diagnosticsやcredentialを保存しない。fresh `pwsh -NoProfile` fixtureはstage copy/readback、credentialed child launch条件、WSLのargv/stdin/report call pathを検証し、ACL・identity/profile/registry・WSL processだけをmockする。fixtureはAPTや実WSL rootを実行しない。stageの作成と呼出し元はnative x64 PowerShell 7.3以上・管理者tokenを要求するが、distroの操作自体は正確なworker SIDの通常tokenを通し、管理者tokenをWSLへ渡さない。

このroot経路はWindows worker SIDが所有する自分のWSL distroに対する限定運用であり、Linux UIDのWindows ownerからの隔離境界ではない。通常のLinux workerはUID 1000の非sudo userとして実行するが、Windows ownerが独自にWSL rootを起動できるというWSLの性質は変わらない。Windows/WSLのhost境界が必要な脅威モデルでは、専用VM等を再評価する。
