# ADR-0006: mise as the Cross-Platform Bootstrap Orchestrator

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0001
- Revises: ADR-0002 installation-channel details

## Context

The repository originally implemented each platform with mostly independent imperative installation logic:

- Ubuntu: APT plus multiple upstream install scripts
- Windows: WinGet plus Store/vendor-specific handling
- macOS candidate: Homebrew/Brewfile
- NixOS: Flake/Home Manager

That made each platform understandable in isolation, but repeated the same portable development tools across several package managers. It also made fresh-machine setup longer than necessary because users had to remember platform-specific bootstrap commands and package-manager details.

mise now provides a machine bootstrap workflow in addition to runtime version management. It can converge host packages through APT, Homebrew formulae/casks, WinGet and other managers, install portable development tools, clone repositories, and run a final bootstrap task.

## Decision

### 1. NixOS remains declarative through Nix

NixOS and NixOS-WSL keep Flake/Home Manager as the machine-state source of truth.

mise MAY be installed on NixOS for project/runtime tool management, but `mise bootstrap` is not the canonical machine-package installer on NixOS.

### 2. mise is the common orchestrator for Ubuntu, macOS and Windows

The canonical flow is:

```text
minimal OS bootstrap
  -> Git + mise
  -> mise bootstrap
     -> host packages/apps
     -> repository checkouts
     -> portable dev tools
     -> final user bootstrap
     -> verification
```

The user does not manually reproduce the full APT/Homebrew/WinGet package list.

### 3. Portable development tools use `[tools]`

Tools whose primary identity is a developer CLI/runtime and which mise can install portably belong in root `mise.toml` `[tools]`.

Current baseline includes:

- Node.js
- Python
- Bun
- Rust
- GitHub CLI
- Infisical CLI
- Claude Code
- Codex
- OpenCode
- Worktrunk
- ripgrep / fd / fzf / jq / bat
- ShellCheck
- Neovim

Project-specific pinned versions still belong to each project. The pc-setup declarations are machine-wide defaults, not a replacement for project-local toolchain definitions.

### 4. Host packages and applications use `[bootstrap.packages]`

Native build libraries, SDKs and GUI applications remain owned by the host package manager, but mise declares and applies them.

Examples:

- Ubuntu: APT
- macOS: mise built-in Homebrew formula/cask manager
- Windows: WinGet

Homebrew is therefore an implementation backend on macOS rather than the user-facing bootstrap entrypoint.

### 5. dotfiles are a downstream bootstrap boundary

`mise.toml` declares the public `rebuildup/dotfiles` checkout under `~/.dotfiles`.

The final `bootstrap` task runs the dotfiles bootstrap on Unix after mise has installed GitHub CLI and Infisical. That bootstrap performs interactive GitHub/Infisical authentication and then obtains private agent-config submodules.

Windows-native dotfiles linking remains disabled until the Windows link adapter is implemented. Windows machine packages and portable tools are still managed by mise.

### 6. Platform scripts become thin adapters

Platform bootstrap scripts MUST NOT duplicate the portable tool inventory.

They may own only:

- installing Git/mise when a fresh OS does not have them
- OS-specific prerequisites needed before mise can run
- vendor/manual boundaries not expressible safely in mise
- platform verification

### 7. One short entrypoint is preferred

Canonical entrypoints:

```text
NixOS / NixOS-WSL:
  nix run 'github:rebuildup/pc-setup?dir=platforms/nixos'

Ubuntu / macOS:
  bootstrap.sh

Windows:
  bootstrap.ps1
```

Once the root scripts are published on main, they may be invoked through a short downloaded bootstrap command. Documentation should keep the underlying recovery path readable.

## Consequences

### Positive

- portable developer tools are declared once
- OS-specific package-manager knowledge moves behind mise
- macOS does not require a separately managed Homebrew installation merely to apply declared formulae/casks
- Ubuntu no longer needs separate installer code for every fast-moving CLI
- Windows CLI/runtime duplication in WinGet can be removed
- fresh-machine setup becomes substantially shorter

### Trade-offs

- mise becomes a bootstrap dependency on non-NixOS platforms
- host package managers still exist underneath and can have platform-specific failure modes
- interactive account authentication remains a separate boundary
- mise bootstrap is sequential rather than transactional; a rerun may be required after a partial failure

## Re-evaluation triggers

Reconsider this decision if:

- mise removes or materially weakens its machine-bootstrap capabilities
- a supported OS cannot reliably use mise
- supply-chain or organization policy requires a different orchestrator
- Nix becomes the canonical host manager on platforms other than NixOS
