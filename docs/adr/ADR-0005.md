# ADR-0005: macOS Remains a Candidate Profile Until Observed on a Real Machine

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0001
- Superseded by: None

## Context

A future macOS development environment is expected, but its actual daily application set and machine-specific configuration have not yet been observed.

Some choices already have high confidence:

- Ghostty is expected to be the primary terminal candidate.
- Amphetamine is expected to be used for keeping the Mac awake when needed.

Many Windows applications may also be useful on macOS, including browser, communication, editor, Android, Adobe, audio, keyboard-remapping, and common CLI tooling. However, copying the Windows inventory wholesale would turn assumptions into false desired state.

The repository contract distinguishes actual environment reproduction from a generic recommendation catalog. Therefore macOS planning must be durable without pretending the planned list is already the maintained environment.

## Decision

### 1. macOS is a candidate profile, not an active platform

Until an actual Mac has been configured and observed, macOS files live under:

```text
plans/macos/
```

They MUST be labeled candidate/planning state.

They are not canonical proof of the maintainer's current environment.

Promotion to `platforms/macos` requires:

1. configuration of a real Mac,
2. installed-application inventory capture,
3. explicit adoption/rejection of candidate applications,
4. verification of platform-specific settings and permissions,
5. replacement of candidate assumptions with observed desired state.

### 2. Homebrew is the primary candidate package graph

Homebrew Formulae/Casks are preferred for software that is actively maintained there.

The candidate profile uses a Brewfile because it can represent both CLI formulae and GUI casks in one reviewable declaration.

Mac App Store-only applications use `mas` where practical.

Applications managed by their own vendor launcher remain explicit child products rather than being hidden behind the launcher.

### 3. Candidate status is recorded per application

The plan distinguishes:

- **High confidence** — explicitly expected for the future Mac.
- **Cross-platform candidate** — currently used/needed elsewhere and likely useful, but not yet adopted on macOS.
- **Vendor-managed candidate** — installed through a parent manager such as Adobe Creative Cloud or Steinberg Download Assistant.
- **Undecided** — requires hardware/workflow evaluation before inclusion.

Ghostty and Amphetamine begin as high-confidence candidates.

### 4. Cross-platform inventory is not automatically inherited

Windows desired state does not imply macOS desired state.

For example:

- Logitech G HUB vs Logi Options+ depends on the actual Mac peripherals and feature needs.
- Warp may be unnecessary if Ghostty becomes the primary terminal.
- Cursor and VS Code may not both remain daily tools.
- kanata may require different macOS permissions/service configuration.
- Cubase/Adobe products depend on license and actual creative workflow on the Mac.
- Android Studio depends on whether Android development is performed locally on that Mac.

These decisions are resolved after actual use, not at planning time.

### 5. Authentication, licenses, permissions, and secrets remain outside package declaration

The candidate Brewfile does not encode account sessions, private keys, API keys, licenses, browser cookies, or macOS privacy permissions.

Accessibility/Input Monitoring/Full Disk Access permissions required by keyboard or automation software are documented and verified only after actual adoption.

### 6. Version snapshots are deferred until a real machine exists

Do not create a fake macOS version snapshot from package repositories.

Once a real Mac exists, capture:

- macOS version/build
- architecture
- Homebrew formula/cask state
- Mac App Store app state
- selected CLI versions
- important application presence
- relevant non-secret system settings

Then reconcile the candidate plan into an active platform.

## Consequences

### Positive

- planning work can begin without corrupting the repository's actual-environment semantics
- Brewfile gives a concise candidate inventory spanning CLI and GUI applications
- high-confidence choices remain distinguishable from speculative cross-platform carryover
- future Mac setup can be compared against a prepared list rather than starting from memory

### Trade-offs

- the candidate Brewfile is not guaranteed to represent the final Mac
- CI can validate file structure but cannot prove an unowned machine's desired state
- some application-specific setup remains intentionally unresolved

## Re-evaluation triggers

Re-evaluate and likely supersede this ADR when:

- the actual Mac is acquired/configured
- a real installed inventory is available
- primary terminal/editor/input-remapping choices are settled
- required creative/audio workflows on macOS are known
- Homebrew/Mac App Store installation channels materially change
