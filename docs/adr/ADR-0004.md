# ADR-0004: Windows Environment Uses a Complete Application Inventory with Mixed Installation Channels

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0001, ADR-0002
- Superseded by: None

## Context

The Windows development machine is not only a CLI environment.

Daily work depends on a mix of:

- browsers and desktop communication apps
- developer editors, terminals, SDK/IDE tooling, and command-line tools
- keyboard/input remapping
- Logitech device software
- Adobe creative applications
- Steinberg/Cubase audio software
- Microsoft Store applications
- portable legacy utilities

Restricting reproduction to WinGet packages would omit important software such as products installed through Adobe Creative Cloud or Steinberg Download Assistant and would misrepresent the actual environment.

Conversely, treating the machine as a raw dump of every installed package would preserve vendor runtimes, stale applications, and incidental system components as if they were desired state.

## Decision

### 1. Windows desired state is a curated complete application inventory

`platforms/windows-11` records all intentionally used software, regardless of whether it is CLI or GUI.

Each entry records its canonical installation owner/channel:

- WinGet community source
- Microsoft Store through WinGet
- vendor application manager
- manual/portable install
- Windows built-in capability

The inventory describes intentional software. It does not automatically promote every item seen in the Windows registry or AppX package list to desired state.

### 2. WinGet package identifiers are exact

For packages available through WinGet, automation uses:

```powershell
winget install --id <package-id> --exact
```

rather than fuzzy package-name matching.

Store apps use the Microsoft Store product identifier and explicit `msstore` source.

### 3. Vendor managers own their child products

Adobe Creative Cloud is installed as a package-manager application, but After Effects and Illustrator remain explicit desired applications installed and authenticated through Creative Cloud.

Steinberg Download Assistant owns Cubase installation/update and its licensing utilities. Cubase remains an explicit desired application in the inventory.

A parent manager being installed is not sufficient evidence that its required child applications are present.

### 4. Legacy/portable tools remain explicit manual steps

ChgKey is intentionally recorded as a manually installed legacy/portable utility because no current trusted package-manager channel is treated as canonical.

Automation must not download an arbitrary mirror merely to make setup fully unattended.

### 5. Keyboard tooling can have overlapping responsibilities

ChgKey and kanata are both recorded when they are intentionally used.

Their presence does not imply they should perform the same remapping layer:

- ChgKey can represent persistent Windows scan-code/registry remaps.
- kanata can represent runtime/layered remapping.

Concrete mappings belong in configuration documentation/files when captured; the installer inventory does not invent them.

### 6. Authentication, licenses, and device/user state are outside install automation

The repository does not store:

- Adobe credentials or licensing state
- Steinberg credentials/license activation
- Discord/Slack/Teams/Linear sessions
- ChatGPT credentials
- Google IME user dictionary unless separately exported through an explicit non-secret workflow
- Logitech cloud/account state
- private keys/tokens

Bootstrap installs software. Interactive login, activation, and user-specific migration remain visible manual gates.

### 7. Desired state and observed machine snapshots are separate

The curated inventory is canonical desired state.

`snapshot.ps1` captures evidence from an actual Windows machine, including:

- WinGet export
- AppX/MSIX package list
- uninstall registry inventory
- selected CLI versions

Snapshot output is review evidence, not an automatic source of truth.

## Consequences

### Positive

- GUI and creative software can no longer silently disappear from environment reproduction.
- Windows setup remains automatable where trusted package channels exist.
- Adobe/Steinberg product managers are represented without pretending their child products are ordinary WinGet packages.
- Incidental vendor runtimes do not pollute desired state.
- New-machine drift can be found by comparing curated inventory against snapshots.

### Trade-offs

- Some applications still require manual installation/login/activation.
- WinGet and Store availability can be region- or publisher-dependent.
- Application presence checks are less uniform than command checks.
- Exact per-app settings are a separate capture problem from application installation.

## Re-evaluation triggers

Re-evaluate when:

- Windows package channels materially change
- a currently manual application gains a trustworthy first-party/package-manager channel
- Adobe or Steinberg changes its installation/activation architecture
- kanata fully replaces a ChgKey responsibility or vice versa
- the actual daily Windows application set changes
- a declarative Windows package/configuration system becomes the preferred source of truth
