# ADR-0026: Rex は OS 公式導入経路で管理し preview channel を追跡する

- Status: Accepted
- Date: 2026-11-21
- Related: Issue #216, rebuildup/dotfiles#207

## Context

Rex (Superlogical) を第二の agent execution runtime の実行基盤として pc-setup の正式管理対象にする。Rex は terminal multiplexer 兼 agent runtime で、client としての Mac app / Windows app と、server としての Linux / Windows / FreeBSD がある。

配布経路の調査結果(2026-11-21 時点):

- `stable` channel は未公開(404)。`preview` / `snapshot` のみ存在し、preview が実質の最新安定候補
- mise registry に Rex backend は存在しない
- Linux: 公式 `install.sh` が apt/dnf/apk 等の repo を追加するか、`--user` で `~/.local/bin` への user install(sudo 不要)、`--tarball` / `--tarball-file` の選択肢がある
- `rex server install` は Linux で systemd user unit(`rex.socket` / `rex.service`)と lingering を自動設定し、Windows では Service(要 admin)または `--user`(HKCU Run)を選べる
- macOS: beta 期間中は Homebrew cask / pkg installer がなく、公式配布は公証済み DMG のみ
- Windows: app / server は tester enrollment が必要で、beta 期間中は全 tester に開放されていない
- NixOS: 公式 flake(`pkgs.superlogical.com/rex/nix/<channel>.tar.gz`)と `rex.nixosModules.default` が存在するが、Linux 向け package は tester package token による認証が必要

## Decision

### 配布 channel

`preview` channel を追跡する。stable が未公開のため選択肢は preview / snapshot のみで、snapshot は不安定 build のため採用しない。stable が公開された時点で channel 選択を再評価する(後述の Consequences)。

version の pin は行わない。pc-setup は継続更新される user tool を snapshot の見た目のために pin しない方針(AGENTS.md §4、ADR-0010)であり、Rex も同じ扱いとする。Linux の `--user` install と macOS DMG install は bootstrap 実行ごとに最新版へ更新され、Windows zip install は install 時に preview release の version と照合して差分があるときだけ再取得する。

### OS ごとの導入経路

- **Ubuntu/WSL** (`platforms/ubuntu-wsl/install-rex.sh`): 公式 `install.sh` を `--user --channel preview` で実行する。`--user` は sudo なしで `~/.local/bin` のみへ binary を置き、systemd が動いていれば installer 自身が `rex server install` を実行する。script は `rex server install` を明示的に再実行する(公式に再実行安全と明記)。systemd user session がない環境では警告に留め、`rex server start` を手動 fallback とする。apt repo を追加する system install は採用しない。理由は、(1) bootstrap が既に `~/.local/bin` 前提の user scope で完結し、(2) repo install でも自動 update は発生せず結局 script 再実行が必要で、(3) 第三者 repo の管理対象を増やさないため。
- **macOS** (`platforms/macos/install-rex.sh`): preview の `latest.dmg` を取得し、読み取り専用 mount から app bundle を `/Applications`(書き込めない場合は `~/Applications`)へ `ditto` で配置する。installed bundle の version/build と DMG 内の値が一致すれば copy を skip する。app は自身の local server を内包するため server 設定は不要。
- **Windows 11** (`platforms/windows-11/install-rex.ps1`): preview の artifact index から windows 向け zip を取得し、SHA-256 を照合して `%LOCALAPPDATA%\Programs\Rex` へ展開する。user PATH への追加と `rex server install --user`(HKCU Run)まで自動化する。Windows Service 化は admin 権限とアカウントパスワード入力を要するため手動境界とする。beta の enrollment 制約があるため、install / server 登録の失敗は bootstrap を止めず、`verify.ps1` も未導入を WARN (pending) として扱う。
- **NixOS**: desired state に含めない。公式 flake と NixOS module は存在するが tester package token が必須であり、secret を repository / flake / Nix store へ埋め込めない。Rex を使う host は host 側 flake input として token を機密境界(`/etc/nix/netrc` 等)で与えて個別に宣言する。

### mise との関係

mise registry に Rex backend は存在しないため `mise.global.toml` の `[tools]` へは追加しない。`mise.global.toml` / `mise.global.lock` は変更しない。導入は platform bootstrap(`scripts/apply-platform.sh` / `bootstrap.ps1`)が呼ぶ platform script が担う。

## Consequences

- 各 OS の bootstrap が Rex を冪等に収束させ、`verify` が binary と server 状態を報告する
- preview channel を追跡するため、Rex 側の preview 更新は次回 bootstrap で自動的に取り込まれる。安定版が必要になった場合や preview の品質問題が出た場合は、channel 指定(`--channel`、DMG path、artifact index の channel)を stable/snapshot へ切り替える ADR 改訂が必要
- `stable` channel 公開時に default install 先を stable へ移すかは別途判断する。`--channel preview` を明示している間は stable 公開後も preview に留まる
- WSL で systemd が無効な構成では server 常駐化は行われず、`rex server start` の手動運用になる。これは verify の WARN で可視化される
- Windows の Service 常駐化と beta enrollment は手動境界として残る。enrollment 完了後に Service 化を自動化するかは実機確認後に再評価する
